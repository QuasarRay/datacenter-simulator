# SET-03 — Remaining manual setup and host-scope gaps

**Medium · Existing usability/scope gaps, not newly broken commands.** The new [docs/GETTING_STARTED.md](https://github.com/QuasarRay/datacenter-simulator/blob/c6aedddfbb9ac569b5e0eb68acc616452bf66136/docs/GETTING_STARTED.md) is an improvement and correctly starts with the portable mode. The following steps still complicate a clean consumer-host setup:

| Surface | Current evidence | Practical consequence and acceptance target |
|---|---|---|
| Optional local dependency checkouts | [simulator/Cargo.toml](https://github.com/QuasarRay/datacenter-simulator/blob/c6aedddfbb9ac569b5e0eb68acc616452bf66136/simulator/Cargo.toml#L33) plus `.gitmodules`; the guide initializes four Rust forks even for default Cargo resolution | Provide one documented minimal bootstrap/check command that verifies exact gitlinks and explains missing paths; preserve fully pinned offline/reproducible builds |
| Native NCCL and driver identities | [simulator/README.md](https://github.com/QuasarRay/datacenter-simulator/blob/c6aedddfbb9ac569b5e0eb68acc616452bf66136/simulator/README.md#L24) requires source build, library search path and a hand-prepared identity JSON | A read-only helper should resolve the intended native libraries, show paths/versions/hashes and emit a reviewable identity file; do not substitute arbitrary system libraries |
| DeepOps image and VFIO plan | [integrations/deepops/config.example.json](https://github.com/QuasarRay/datacenter-simulator/blob/c6aedddfbb9ac569b5e0eb68acc616452bf66136/integrations/deepops/config.example.json) has an all-zero image hash and sample PCI addresses, intentionally unusable unchanged | Add a config preparation flow that verifies an image, inventories candidate devices and produces a plan without rebinding host drivers; refusal should identify the placeholder before costly staging |
| Host/path restrictions | [simulator/src/evidence.rs](https://github.com/QuasarRay/datacenter-simulator/blob/c6aedddfbb9ac569b5e0eb68acc616452bf66136/simulator/src/evidence.rs#L51) is compiled without a target guard; native paths depend on Linux `/proc`, namespaces and device nodes | Do not imply Windows-native portability from “portable model”; either state Linux/Unix build scope explicitly or add target-gated portable support and CI. WSL/native Windows were not tested here |
| VM footprint and retained run directories | `vm::preflight` requires a new state directory; the example requests 20 GiB RAM and sizable virtual disks | Add a plan-aware capacity report and an explicit owned-artifact cleanup/inventory command. Preserve evidence until the user chooses cleanup; do not silently delete previous disks |
| Backend choice | Namespace execution, VM execution, Mokka and EX457 have separate prerequisites; no Incus backend is present | Keep the guide explicit about capability versus host cost. Do not force a VM fleet where analytical/control-plane or namespace execution satisfies the scenario |

NetBox also has no configured extra-CA input in `NetBoxConfig`/`NetBoxClient::new`; enterprise private-PKI deployment needs an explicit trust configuration rather than advice to disable HTTPS. The exact trust-store behavior must be checked against the pinned reqwest build before prescribing host-specific changes.

**Verification plan:** run the minimal supported path from a clean checkout as a normal user on the documented Linux distributions, then exercise each optional path independently. Record download/build disk footprint and time; no measurements of those costs are claimed in this report. Treat privileged policy changes, GPU rebinding and cluster deployment as separate explicit operational actions.
